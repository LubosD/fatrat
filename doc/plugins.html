Writing a FatRat plugin

A FatRat plugin is a Python module that teaches FatRat about links it does not otherwise understand — typically a file host, where the link the user has is a web page and the real download URL has to be scraped out of it. The plugin does the scraping; the downloading stays FatRat's job, so a plugin's transfers get segmenting, speed limits, resume and the rest without asking.

The shape of one

import fatrat

@fatrat.download_plugin(name="Example.com", url_pattern=r"https?://example\.com/f/\w+")
class Example(fatrat.DownloadPlugin):
    async def process_link(self, url):
        page = await self.fetch(url)
        token = page.search(r'name="token" value="([^"]+)"')
        if not token:
            raise fatrat.PluginError("no download token on the page")

        await self.wait(30)
        answer = await self.solve_captcha(page.urljoin("/captcha.png"))

        final = await self.fetch(url, data={"token": token, "captcha": answer})
        self.start_download(fatrat.DownloadUrl(url=final.json()["link"], referrer=url))

Plugin code runs on FatRat's main thread, so it must never block it: anything slow is awaited. Everything you can await is something FatRat does for you — a page fetch, a countdown, a captcha — and the coroutine resumes when it is done.

What a download plugin can use

await self.fetch(url, data=..., headers=...) Fetch through FatRat: this transfer's cookie jar, the configured proxy, FatRat's user agent. data makes it a POST (a mapping is form-encoded). Gives a Response with .text, .content, .headers, .json(), .search(pattern), .urljoin(url) and .filename.
await self.wait(seconds) A countdown the user can watch, instead of a transfer that looks stuck.
await self.solve_captcha(url) Hands the image to whichever captcha front-end is configured. Raises fatrat.CaptchaError if nobody solved it.
self.start_download(url_or_DownloadUrl) Hand the resolved link back and finish. Your cookies come along.
self.report_file_name(name) Name the transfer when the link does not carry a usable name.
self.vars["key"] Values saved with the transfer, still there after a restart.
fatrat.settings["myplugin/user"] FatRat's settings, including whatever your plugin.json declares.
await fatrat.run_in_thread(fn, ...) The one way to leave the main thread, for genuinely CPU-bound work. It must not touch FatRat's API.
self.log(message), self.fail(message) Write to this transfer's log; fail it with a message the user reads.

Two more methods are worth overriding: final_check(path), which gets the finished file so you can reject the HTML error page a host served with a 200, and on_failed(), to drop state when a transfer fails. Anything you raise out of process_link fails the transfer with that text, so write those messages for a user rather than for a log.

Packaging

A plugin is a directory with a plugin.json manifest next to the module: 

{
  "schema": 1,
  "name": "example",
  "version": "1.0.0",
  "api": "1",
  "entry": "example.py",
  "license": "GPL-3.0-only",
  "config": [
    {"type": "text", "key": "example/user", "title": "Username"},
    {"type": "password", "key": "example/password", "title": "Password"}
  ]
}

The config list is your settings page: FatRat renders it in the desktop settings dialog and in the web interface, and the values land in the settings keys you name.

Dependencies

Most plugins need nothing but the standard library and fatrat. When yours genuinely needs a library, list it in the manifest: 

  "dependencies": ["feedparser"]

FatRat will not install those packages as a side effect of installing your plugin: it names them and asks first, because they come from PyPI rather than from the repository the user chose. They are then fetched with pip into a _vendor directory inside your plugin, so two plugins may depend on different versions of the same package, and removing a plugin removes its dependencies with it. Keep the list short: every entry is one more thing the user has to trust.

Publishing

There is no central plugin index. You publish a repository — a git repository, or any directory — with a fatrat-plugins.json at its root listing what it offers, and users add it by URL under Settings → Extensions. FatRat records the exact commit it installed, so updates are something a user chooses.

The FatRat source ships a complete example under examples/plugin-repo/: a repository manifest and a commented dummy plugin that exercises fetching, a countdown, a captcha and final_check. Adding that directory as a repository is also the way to develop a plugin, since a local repository is used where it lies.

A plugin runs with your full user privileges — the same trust you extend to anything else you install from a git repository. FatRat shows the source and the revision before it installs anything, and a plugin can be switched off again under Settings → Extensions, or all of them at once with fatrat --no-python.
